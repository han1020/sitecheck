설치 경로 확인 — 명령을 치기 전에
이 문서의 명령은 설치 디렉터리를 셸 변수 SC로 씁니다. 현재 값은 /root/achee7059/siteCheck이지만 서버 정리나 계정 변경으로 바뀔 수 있으니, 작업 전에 실제 위치를 확인하고 각 명령 블록 첫 줄의 SC=…를 맞추세요. 실제 위치는 운영 중인 것에서 읽는 게 가장 확실합니다. 
# ① 웹 컨테이너가 떠 있을 때 — compose 를 실행한 디렉터리가 그대로 나온다
docker inspect sitecheck-web --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'
   출력 예: /root/achee7059/siteCheck

# ② 타이머가 설치돼 있을 때 — '=' 뒤가 경로
grep WorkingDirectory /etc/systemd/system/sitecheck-collect.service
   출력 예: WorkingDirectory=/root/achee7059/siteCheck

# ③ 둘 다 없을 때 — 후보 디렉터리 찾기 (docker-compose.yml 이 있는 곳이 설치 경로)
ls -d /root/*/siteCheck /opt/siteCheck 2>/dev/null
   출력 예: /root/abc/siteCheck

# ④ 위에서 나온 경로를 그대로 적는다 (끝에 / 없이)
SC=/root/achee7059/siteCheck          # 예) 경로가 바뀌었다면  SC=/root/abc/siteCheck
ls "$SC/docker-compose.yml"           # 이 파일이 보이면 경로가 맞는 것
①이 되는 상황이면 한 줄로 자동 설정할 수도 있습니다: SC=$(docker inspect sitecheck-web --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'). ①과 ②의 결과가 서로 다르면(컨테이너와 유닛의 경로가 다름) 이전 설치가 남아 있는 것이니 둘 중 하나를 정리한 뒤 진행합니다. SC는 터미널을 새로 열 때마다 다시 설정합니다.

읽기 전에 — 용어와 약속

이 문서를 쓰는 두 사람

  • 개발 담당 — 코드를 고치고 GitHub에 올립니다 (2절의 1·2번).
  • 운영 담당 — 188 서버에서 새 코드를 받아 적용하고, 수집이 잘 도는지 보고, 화면에서 판단이 필요한 공지를 처리합니다 (2절의 3·4번과 3~7절). 코드를 직접 고칠 일은 없습니다.

서버에 들어가는 법

188 서버는 화면이 없는 리눅스 컴퓨터입니다. 내 PC의 터미널(macOS "터미널" 앱, Windows "PowerShell")에서 아래처럼 접속하면 글자로 명령을 내릴 수 있습니다. root는 관리자 계정이고, 비밀번호나 키는 서버 담당자에게 받습니다.

ssh root@<188 서버 IP>        # 접속. 프롬프트가 root@k8s-n10:~# 로 바뀌면 들어온 것
exit                              # 나가기

명령 복사 요령

  • 회색 상자의 명령은 한 줄씩 복사해 붙여넣고 Enter. 여러 줄을 한꺼번에 붙이면 중간에 끊겨 엉뚱하게 실행될 수 있습니다.
  • # 뒤의 글은 설명입니다. 같이 붙여넣어도 무시됩니다.
  • <188 서버 IP>처럼 꺾쇠로 싸인 부분은 실제 값으로 바꿔 넣습니다(꺾쇠는 빼고).
  • $SC는 "설치 경로"를 담아 둔 이름표(변수)입니다. 명령을 치기 전에 SC=/root/…/siteCheck 한 줄로 값을 넣어 두면 이후 명령의 $SC가 그 값으로 바뀝니다. 터미널을 새로 열면 다시 넣어야 합니다.
  • 명령이 끝나고 아무 말이 없으면 보통 성공입니다. 빨간 글씨나 error, failed가 보이면 7절을 보세요.
용어뜻
저장소 / 커밋 / 푸시코드를 보관하는 GitHub 공간. 고친 내용을 기록하는 것이 커밋, 그 기록을 GitHub로 올리는 것이 푸시. 서버는 git pull로 그 기록을 받아 옵니다.
이미지 / 컨테이너 (Docker)이미지는 프로그램과 필요한 부품을 한 덩어리로 포장한 것(docker compose build로 만듦), 컨테이너는 그 이미지를 실제로 실행한 것(up -d web으로 띄움). 코드를 바꾸면 이미지를 다시 만들어야 컨테이너에 반영됩니다.
볼륨컨테이너 밖(서버 디스크)에 두는 폴더. 엑셀·이력·설정(output/, config/, logs/)은 볼륨이라 컨테이너를 바꿔도 남습니다.
systemd / 타이머 / 로그리눅스가 서비스와 예약 실행을 관리하는 기능. systemctl로 켜고 끄고 상태를 보고, journalctl로 그 서비스가 남긴 로그(기록)를 봅니다. 화·금 자동 수집이 이 타이머입니다.
저장 APIDB에 직접 붙는 대신 거치는 창구 서버(dashboard-server, 9092 포트). SiteCheck는 "이 공지 저장해 줘 / 고쳐 줘 / 지워 줘"를 이 창구에 요청하고, 창구가 DB를 바꿉니다.
itemIdDB가 공지마다 붙이는 번호(예: 49). 엑셀의 숨긴 H열에도 적혀 있어 "이 엑셀 행 = DB의 그 공지"를 잇는 이름표입니다.
소프트 삭제DB 행을 실제로 지우지 않고 "삭제됨" 시각(del_dt)만 적어 두는 방식. 다시 살릴 수 있고, 조회 때는 빠집니다.
해시 (dedup_hash)공지의 다섯 값을 섞어 만든 고유 지문. 지문이 같으면 같은 공지로 보고 DB가 두 번 저장하지 않습니다.

2. 코드 수정 → 커밋·푸시 → 188 반영

188의 컨테이너는 이미지 안에 들어 있는 코드로 돕니다. 그래서 서버에서 git pull만 해서는 아무것도 바뀌지 않고, 이미지를 다시 빌드해 컨테이너를 교체해야 합니다. 순서는 다음과 같습니다.

개발 담당 1·2번   운영 담당 3·4번. 운영 담당은 개발 담당이 "푸시했다"고 알려오면 3번부터 하면 됩니다.

  1. PC에서 고치고 테스트한다 (개발 담당)

.venv/bin/python -m pytest -q          # 출력 예: 34 passed in 0.6s  (failed 가 있으면 푸시하지 않는다)
    DB 연동 모듈(src/notice_*.py)을 건드렸다면 테스트가 특히 중요합니다. 가짜 API(tests/test_notice_sync.py의 FakeApi)로 재수집·후보·수정·삭제·장애 시나리오를 돌립니다.
  2. 커밋하고 푸시한다 (개발 담당)

  3. 188에 접속해 받고, 빌드하고, 교체한다 (운영 담당)

같은 서버의 다른 Docker 서비스와 섞이지 않게
188에는 다른 컨테이너들도 떠 있습니다. 이 프로젝트가 건드리는 것은 이미지 sitecheck:latest, 컨테이너 sitecheck-web과 수집 때 잠깐 생겼다 사라지는 sitecheck-collect-run-…, 네트워크 sitecheck_default, 호스트 포트 9095, systemd 유닛 sitecheck-collect.*, /etc/sitecheck/뿐입니다. 그 밖의 것은 손대지 않습니다.
  • docker compose 명령은 반드시 설치 디렉터리(현재 /root/achee7059/siteCheck, 바뀔 수 있음) 안에서 실행합니다. 다른 디렉터리에서 실행하면 그 디렉터리의 프로젝트에 적용됩니다
  • docker system prune, docker image prune -a, docker network prune, docker volume prune은 쓰지 않습니다 — 다른 서비스의 멈춰 있는 이미지·네트워크·볼륨까지 지웁니다. 정리가 필요하면 docker image rm <sitecheck 이미지 ID>처럼 이름을 지정합니다
  • docker compose down은 이 프로젝트의 컨테이너·네트워크만 내리지만 -v, --remove-orphans는 붙이지 않습니다. 웹만 재시작할 때는 docker compose restart web 또는 up -d web
  • Docker 데몬 설정(/etc/docker/daemon.json), iptables, 다른 compose 파일은 건드리지 않습니다. 포트는 9095 하나만 씁니다
  • 수집 중(화·금 10:00·14:00 직후 수 분)에는 Chromium이 CPU·메모리(공유메모리 1g)를 씁니다. 같은 노드의 다른 서비스가 민감하면 타이머 시각을 deploy/docker/sitecheck-collect.timer의 OnCalendar=로 옮기세요

3. 자동 수집 타이머 다루기

자동 수집은 리눅스의 예약 실행 기능(systemd)으로 돕니다. 아래 명령 중 systemctl은 켜고 끄고 상태를 보는 것, journalctl은 로그를 보는 것입니다. 타이머는 호스트의 systemd 유닛 두 개입니다. sitecheck-collect.timer가 시각이 되면 sitecheck-collect.service를 부르고, 그 서비스가 docker compose --env-file /etc/sitecheck/api.env run --rm collect를 실행합니다. 컨테이너를 쓰기 때문에 저장소의 deploy/docker/ 유닛을 씁니다(deploy/ 바로 아래의 유닛은 venv 방식용).

3-1. 설정돼 있는지 확인

systemctl list-timers sitecheck-collect.timer --no-pager   # 한 줄 나오면 동작 중. "0 timers listed" 면 꺼져 있거나 미설치
systemctl is-enabled sitecheck-collect.timer               # enabled / disabled / "No such file" (= 미설치)
grep -E 'WorkingDirectory|ExecStart' /etc/systemd/system/sitecheck-collect.service   # 경로·--env-file 이 맞는지
결과상태할 일
NEXT Tue 2026-10-13 10:00:00 KST … 한 줄, enabled정상journalctl -u sitecheck-collect.service -n 20로 마지막 실행만 확인

4. DB에 저장되는 방식

4-1. 언제 저장되나

  • 수집이 끝났을 때 — 엑셀 파일이 저장된 직후, 그 파일의 모든 행(일반점검 + 정기점검)을 API에 보냅니다. 수집한 원본이 아니라 엑셀의 최종 행을 보내는 이유는, 엑셀에는 전날에서 이어진 행(carryover)과 담당자가 고친 값이 들어 있기 때문입니다.
  • 엑셀뷰에서 DB 동기화 버튼을 눌렀을 때 — 선택한 파일을 통째로 다시 보냅니다. 판단 필요 행을 처리한 뒤나 오류 뒤 재시도에 씁니다.
  • 엑셀뷰에서 편집·삭제·검토 탭 공지추가를 했을 때 — 그 행만 즉시 API를 거친 뒤(수정은 PATCH, 삭제는 DELETE, 추가는 저장) 파일에 반영합니다. API가 실패하면 파일도 바뀌지 않습니다.

4-3. "같은 공지"를 어떻게 알아보나

4-2 표에서 식별값 ✓ 표시가 된 다섯 항목 — 구분·기관코드·기관명·일시 원문·업무 — 이 항목들로 검증합니다. 이 다섯 값이 공지의 정체성입니다. 다섯 값에서 앞뒤 공백과 영문 대소문자 차이를 없앤 뒤 하나로 섞어 고유한 지문(해시)을 만들고, DB는 지문이 같은 행을 두 개 두지 않습니다. 그래서 같은 공지가 매번 수집돼도 DB에는 한 행만 있습니다. 사유는 정체성에 들어가지 않습니다 — 사이트가 사유 문구를 바꿔도 같은 공지로 봅니다.

이런 입력이 다시 오면DB 판단엑셀에 남는 값
다섯 값이 모두 같고 사유도 같음같은 공지 — EXISTINGDB의 현재 값
다섯 값은 같고 사유만 다름같은 공지 — REASON_PRESERVEDDB의 사유 (담당자가 고친 값이 살아남음)
업무의 영문 대소문자만 다름 (A사이트 / a사이트)같은 공지DB에 먼저 저장된 원문
일시 원문이 다름 (00:00~06:00 → 00:00~07:00)다른 공지 — 새로 INSERTED두 행 모두. 기존 공지는 자동으로 지우지 않음
구분·기관·일시는 같은데 업무 문구가 다름자동 판단 안 함 — 판단 필요사람이 결정할 때까지 저장 보류 (4-5)
이미 삭제된 공지와 같은 값SUPPRESSED_DELETED — 재등록 거부엑셀에서 그 행이 제거되고 "삭제 제외 n건"으로 집계

4-4. 저장 결과 상태

상태뜻DB 변화
INSERTED처음 보는 공지새 행
EXISTING이미 있는 공지, 사유도 같음없음
REASON_PRESERVED이미 있는 공지, 사유만 다름 — DB 사유 유지없음
LINKED_EXISTING사람이 "기존 공지에 연결"하기로 결정한 행없음 (연결 대상의 값을 사용)

화면의 "DB 저장 n건"은 이 다섯 상태 중 SUPPRESSED_DELETED를 뺀 넷의 합, 즉 DB와 맞춰진 행 수입니다. 새로 생긴 행 수가 아닙니다. 예를 들어 정기점검 11행은 이미 DB에 있어 매번 EXISTING으로 11건이 세어집니다.

4-5. 판단 필요 — 사람이 결정하는 유일한 경우

같은 기관의 같은 일시에 업무 문구만 다른 공지가 DB에 있으면, 그것이 같은 작업의 표현 차이인지 정말 다른 작업인지 기계는 모릅니다. 그래서 저장을 멈추고 판단 필요로 올립니다. 담당자의 선택은 세 가지입니다.

선택결과다음 수집부터
기존 공지에 연결그 공지의 DB 값(업무·사유)을 사용. 엑셀 행이 DB 값으로 바뀜같은 입력이 와도 자동으로 같은 공지에 연결
별도 신규 등록다른 공지로 새 행 생성자동으로 신규 처리 (정확히 같은 값은 중복 생성 불가)
보류DB에 저장하지 않음계속 판단 필요로 표시

이 결정은 188 서버의 output/state/production/notice_state.json에 기록됩니다. DB에는 없는, SiteCheck만의 기억입니다. 이 파일이 사라지면 과거의 연결 결정을 다시 해야 하므로 백업 대상입니다.

4-6. 담당자가 고친 값은 어떻게 지켜지나

  • 엑셀뷰에서 사유·업무·기관명을 고쳐 저장하면 그 공지에 "이 값으로 고쳐 줘"(PATCH) 요청이 가고, DB에 담당자 값이 남습니다. 다음 수집이 사이트의 옛 문구를 다시 가져와도 DB는 REASON_PRESERVED/연결로 답하고, 엑셀은 다시 담당자 값으로 돌아옵니다.
  • 일시를 고치면 다른 공지가 됩니다. 저장 시 확인창이 뜨고, 수락하면 새 공지가 만들어지고 기존 공지는 그대로 남습니다. 기존 공지를 지울지는 담당자가 따로 결정합니다(행 삭제).
  • 행을 삭제하면 DB에서는 지워지지 않고 del_dt만 찍힙니다(소프트 삭제). 이후 같은 공지가 다시 수집돼도 SUPPRESSED_DELETED로 억제되어 엑셀에 다시 나타나지 않습니다. 되살려야 하면 DB 담당자가 del_dt를 NULL로 바꾼 뒤 엑셀뷰에서 DB 동기화를 한 번 실행합니다.

4-7. 타팀이 조회할 때 알려줄 것 DB 담당·타팀 전달용

운영 담당이 직접 실행하는 내용은 아닙니다. DB를 직접 조회하는 팀에 아래 조건을 그대로 전달하면 됩니다.

-- 진행 중인 일반점검 (삭제 제외, 종료 시각이 지금 이후)
SELECT item_id, institution_code, institution_name, schedule_text, service_text, reason_text, window_start, window_end
FROM GDS.TB_SITE_CHECK
WHERE del_dt IS NULL AND check_type = '일반점검' AND window_end >= NOW()
ORDER BY window_start;

-- 정기점검 (반복 일정이라 window_* 는 NULL)
SELECT institution_name, schedule_text, service_text, reason_text
FROM GDS.TB_SITE_CHECK
WHERE del_dt IS NULL AND check_type = '정기점검';
  • del_dt IS NULL을 붙여야 삭제된 공지가 빠집니다.
  • 모든 시각은 KST(+09:00)로 저장돼 있습니다. UTC로 해석하면 9시간 어긋납니다.
  • 정기점검의 window_start/window_end는 NULL입니다. 일시는 schedule_text 원문("매월 셋째주 일요일 00:00 ~ 07:00")을 보세요.
  • 타팀 계정은 SELECT 전용입니다. 수정·삭제는 SiteCheck 화면을 통해서만 합니다.

4-8. API가 죽어 있으면

수집은 그대로 끝나고 엑셀과 감지 이력은 남습니다. 동기화만 건너뛰고 상태줄에 빨간 글씨로 "DB 동기화 오류 n건"이 표시되며, 로그에 같은 문구가 남습니다. 못 보낸 행은 다음 수집 때 자동으로 다시 보냅니다 — 같은 공지를 두 번 보내도 DB는 한 행만 두므로 따로 복구할 것이 없습니다. API가 돌아온 뒤 바로 반영하고 싶으면 엑셀뷰에서 DB 동기화 버튼을 누르면 됩니다.

같은 행이 두 줄로 보임"기존 공지에 연결" 후 두 행이 같은 공지를 가리킴정상. 하나를 지우면 둘 다 지워짐
타이머 수집이 15분 만에 중단systemd TimeoutStartSec=900 초과 — 사이트 응답 지연journalctl -u sitecheck-collect.service에서 멈춘 사이트 확인
지금 수집에서 Chromium 오류이미지의 브라우저 문제 또는 공유메모리 부족docker compose build 재실행, compose의 shm_size: 1g 유지
9095가 밖에서 안 열림노드 방화벽은 Docker 포트만 허용 — 호스트 프로세스로 띄우면 막힘반드시 컨테이너로 운영. 그래도 안 되면 9092를 연 곳에 9095 추가 요청. 임시로 ssh -N -L 9095:127.0.0.1:9095 root@<188> 후 http://localhost:9095

엑셀 전용으로 급히 되돌리려면: systemctl disable --now sitecheck-collect.timer → docker compose up -d web(env-file 없이) → 타이머 유닛의 --env-file … 제거 후 daemon-reload → 타이머 재개. DB에 저장된 공지는 그대로 남습니다.

8. 보안·환경 메모

/etc/sitecheck/api.env 188 서버 안의 파일

이 파일은 188 서버에만 있습니다 — PC에도, GitHub 저장소에도 없습니다. ssh로 들어가서 cat /etc/sitecheck/api.env로 보고, 고칠 때는 아래 nano를 씁니다. 서버를 옮기면 이 파일도 새 서버에 다시 만들어야 합니다.

SITECHECK_API_BASE_URL=http://<API 서버 IP>:9092
SITECHECK_API_ENV=production
SITECHECK_API_AUTH_HEADER=X-Auth-User-Email
SITECHECK_API_AUTH_VALUE=<서비스 계정>@gowid.com
  • 고칠 때: nano /etc/sitecheck/api.env → 수정 → Ctrl+O, Enter(저장) → Ctrl+X(닫기) → docker compose --env-file /etc/sitecheck/api.env up -d web으로 재기동해야 반영
  • root만 읽음(0600). Git·문서에 실제 값을 적지 않음
  • http://가 없으면 프로그램이 시작하지 않음
  • production이면 시험용 쓰기 명령(--write)이 거부됨

접근 통제

  • 저장 API 인증은 헤더 이메일의 도메인(@gowid.com)만 검사합니다. 내부망 격리가 전제이며 외부에 노출하면 안 됩니다
  • 대시보드(9095)에는 로그인이 없습니다. 사내망 IP에만 열고, 필요하면 Nginx Basic Auth를 앞에 둡니다
  • GitHub 저장소는 공개입니다. 서버 주소·계정·비밀번호·내부 IP를 커밋하지 않습니다
  • 타팀 DB 계정은 SELECT 전용으로 발급합니다
