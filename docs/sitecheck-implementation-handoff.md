# SiteCheck 프로젝트 작업 명세
최종본 1.3 · 2026-09-28 · 이 저장소의 구현 담당자용

## 1. 작업 범위와 산출물

현재 Python 수집·엑셀 프로젝트에 저장 API 연동, 수동 연결/보류의 로컬 상태, 엑셀 편집·삭제 연동을 추가한다. 전체 시스템 DB 전환은 아니다. 타팀은 184의 GDS.TB_SITE_CHECK 테이블을 조회한다.

- 종합 보고서: [sitecheck-project-analysis.html](sitecheck-project-analysis.html)
- 별도 API 프로젝트 계약: [sitecheck-api-spec.md](sitecheck-api-spec.md)
- API 프로젝트가 적용할 DDL: [site_check_item.mysql.sql](sql/site_check_item.mysql.sql)
- DB 주소·계정·스키마·접속 조건은 사용자가 API 프로젝트에 직접 전달한다. 이 프로젝트는 DB에 직접 연결하지 않는다.
- API 담당자가 테스트/운영 Base URL·인증 전달 방식·접속 조건을 회신하면 이 프로젝트에서 테스트한다.
- 이 저장소에는 식별 규칙, API 클라이언트, 로컬 결정 파일, 엑셀 숨김 ID, 수집·검토 추가·엑셀 수정/삭제 연동을 구현했다. 모의 API 테스트는 통과했지만 실제 테스트/운영 API 서버 연결 및 DB 결과 검증은 아직 하지 않았다. 실제 서버 주소·인증을 받은 뒤 [연동 검증 절차](sitecheck-integration-test.md)를 수행한다.

## 2. 확정 동작

| 상황 | 처리 |
|---|---|
| 동일한 5개 식별 값 재수집 | 기존 ID·담당자가 수정한 현재 값 사용 |
| 사유만 다름 | 기존 공지·사유 유지 |
| 식별 정규화 후 일시 원문이 다름 | 신규 공지. 기존 공지는 사람이 삭제 여부 판단 |
| 업무 등 식별 필드의 영문 대소문자만 다름 | 같은 공지. 기존 원문과 담당자 수정값 유지 |
| 식별 정규화한 구분·기관코드·일시는 같고 기관명/업무가 다름 | 후보 비교 후 기존 연결·신규·보류 |
| 정확 키 또는 유효 연결 대상이 삭제됨 | 재등록 금지 |
| 명시적 PATCH | 마지막 DB 반영 우선. 일시 변경은 신규 등록으로 전환 |
| 엑셀 행 삭제 | 해당 ID를 API로 soft 삭제 |
| 초기 적재 | 최신 파일 한 개만. 과거 파일은 가져오지 않음 |
| 저장 후 일정 종료 | DB에 보관. 만료로 DELETE하지 않음 |

구분·기관코드의 저장값은 API의 normalize 규칙을 따른다. 입력 식별키·후보·수동 연결의 비교와 로컬 해시는 API 명세의 normalize_for_identity(casefold 포함)를 동일하게 사용한다. 원문 대소문자는 표시용으로 보존한다. 시작/종료 파싱값이 같다고 서로 다른 일시 원문을 임의 병합하지 않는다. 동일 게시물 URL이어도 식별 정규화한 일시가 다르면 신규 공지다. MySQL의 utf8mb4_unicode_ci 비교 결과만으로 해시 중복을 판정하지 않는다.

## 4. 공통 저장 흐름

1. 엑셀 저장 성공 후 점검 시트 B:G의 최종 6개 값을 읽고 시각을 산출한다. 원본 hits만 보내면 carryover·수정값·정기점검이 빠진다.
   현재 DDL의 문자열 길이 제한(기관코드 10자, 기관명 100자, 일시·업무·사유 각 200자)을 먼저 확인하고 넘는 행은 보완 대상으로 남긴다.
2. 사용자 결정 이전 입력의 정규화 5개 값을 보관한다. API 결과로 엑셀 값을 바꾸더라도 원래 입력과의 연결을 잃지 않는다.
3. 환경별 로컬 결정에서 HOLD면 저장하지 않고 보류 목록에 유지한다. LINK면 linkedItemId로 API에 검증을 요청한다. NEW_ALLOW면 신규 승인 상태로 저장 요청한다.
4. 결정이 없는 행은 :lookup으로 정확 키를 조회한다. FOUND/DELETED는 저장 API의 기존/삭제 억제 처리를 사용한다.
5. 정확 키가 없으면 GET 목록에 checkType/institutionCode/scheduleText/includeDeleted=true를 보내 후보를 끝까지 조회한다.
6. 같은 일시 후보가 없으면 신규로 저장한다. 후보가 있으면 비교 화면으로 보낸다. 다른 일시의 공지는 후보에서 제외한다. 삭제 후보만 있어도 자동 복원하거나 임의 병합하지 않고 검토한다.
7. 미결정 행은 일괄 저장에서 제외하고 제외 건수·보류 사유를 명시한다. 누락처럼 숨기지 않는다. API에는 승인/자동 판정이 끝난 행만 전송한다.
8. 신규/기존/연결 응답의 실제 item 값으로 현재 엑셀 행과 연결 정보를 맞춘다. SUPPRESSED_DELETED는 현재 엑셀의 정상 공지 행에서 제외하고 억제 건수로 표시한다. 삭제 상태의 응답 item을 정상 행으로 다시 쓰지 않으며 로컬 연결 기록은 유지한다.
9. 같은 입력 키는 DB 정확 중복 검사를 항상 거친다. 수동 신규 선택도 완전히 동일한 키를 두 건 만들 수는 없다.

후보 조회와 저장 사이에 데이터가 바뀔 수 있다. 정확 키·연결 대상은 저장 API에서 다시 검증한다. 후보는 업무 비교를 위한 정보이며 동시 다른 식별키 저장을 완전히 막는 유일성 제약은 아니다. 같은 키의 중복은 DB UNIQUE가 보장한다.

### 시각 처리

- 최종 일시가 수집 원문과 일치하면 hit_to_dict의 window_start/window_end를 사용할 수 있다.
- 편집된 일시·carryover·최신 엑셀 적재는 최종 일시를 파싱한다. 시간대 없는 한국 사이트 원문은 Asia/Seoul이다.
- API 요청의 시작·종료 시각에는 +09:00을 명시한다. API는 오프셋이 다른 입력도 KST로 바꿔 저장하며 응답도 +09:00으로 돌려준다. 엑셀에 반환 시각을 표시할 때 UTC로 재해석하지 않는다.
- window_start/window_end는 초 단위 DATETIME(= DATETIME(0))이다. 수집·파싱 결과에 0이 아닌 소수 초가 있으면 조용히 반올림·절삭하지 않고 보완 대상으로 처리한다. 소수 초가 0인 입력은 허용한다. crt_dt/up_dt/del_dt도 같은 정밀도이며 API 응답의 createdAt/updatedAt/deletedAt에 대응한다. 모든 응답 시각에는 소수점이 없다.
- 실제 날짜가 없거나 명확히 해석할 수 없는 각 시각은 null. 반복 일정도 null. 시작을 종료로 대체하지 않는다.
- 두 시각이 있으면 시작 <= 종료. 파싱값 보정은 PATCH가 가능하지만 원문 일시 변경을 같은 공지 수정으로 우회하지 않는다.

## 5. 수동 연결 기록의 저장

**단일 MySQL 업무 테이블을 유지하는 구현 선택:** 연결·보류·재시도 상태는 이 프로젝트의 환경별 로컬 파일에 둔다. API가 다른 서버에서 동작해도 linkedItemId와 입력 값을 검증하므로 DB에 별도 연결 테이블을 만들지 않는다.

권장 파일: output/state/{environment}/notice_state.json.
environment는 API 대상별 고유 설정명이다. 테스트/운영 연결을 섞지 않는다. 파일은 매 수집 결과가 아니라 지속 운영 상태이므로 run JSON 삭제·엑셀 정리와 함께 지우지 않는다.

~~~json
{
  "schemaVersion": 1,
  "environment": "test",
  "decisions": [
    {
      "inputIdentityHash": "식별정규화_casefold_5개_값의_SHA256",
      "inputIdentity": {
        "checkType": "일반점검",
        "institutionCode": "KRBK0101",
        "institutionName": "저축은행중앙회",
        "scheduleText": "2026.09.19(토) 00:00 ~ 06:00",
        "serviceText": "수집된 업무 표현"
      },
      "action": "LINK",
      "itemId": "101"
    }
  ],
  "pendingOperations": []
}
~~~

- action은 LINK / NEW_ALLOW / HOLD다. LINK만 itemId가 필요하다. 로컬 해시가 같을 때는 원문이 아닌 식별 정규화한 5개 값으로 실제 충돌 여부를 구별한다. 대소문자만 다른 원문은 같은 입력 결정으로 처리한다.
- 기존 공지 연결: 선택 결과를 내구성 있게 기록하고 API 검증 성공 시 확정한다. 저장 실패/대상 변경은 보류 또는 결과 확인 상태로 남긴다.
- 다음 수집에서도 linkedItemId를 전달한다. API는 같은 구분·기관코드·일시인지와 삭제 여부를 재검증한다.
- 연결 대상이 삭제되면 기록을 지우고 신규 등록하지 않는다. SUPPRESSED_DELETED로 유지한다.
- LINK_TARGET_CHANGED/IDENTITY_ALREADY_ASSIGNED는 자동 덮어쓰기나 신규 우회 없이 검토로 돌린다.
- 기관명·업무를 PATCH할 때에는 변경 전 5개 값 → 기존 ID 연결 의도를 API 호출 전에 pendingOperations에 남긴다. 성공 후 LINK로 확정해 예전 수집값이 돌아와도 담당자 수정값을 사용한다.
- 구분·기관코드가 달라지는 경우 이전 연결을 자동 유지하지 않는다. API 검증 결과에 따라 다시 검토한다.
- 일시 변경은 신규다. 이전 일시 입력을 새 공지에 연결하는 기록을 만들지 않는다.
- 단일 운영 상태 경로를 CLI·웹이 공유한다. 프로세스 내 Lock만으로 부족하므로 프로세스 간 파일 잠금과 임시 파일→원자적 교체를 사용한다. 실패 시 파일을 빈 상태로 덮어쓰지 않는다.
- 연결 상태는 업무 수정 이력은 아니지만 운영 필수 정보다. DB와 함께 백업·복구하고 저장 위치는 디스크 영속성이 보장돼야 한다. API 키·비밀번호는 넣지 않는다.
- 여러 수집 호스트가 각자 다른 상태 파일을 사용하면 수동 결정이 공유되지 않는다. 초기 범위는 하나의 상태 저장소/운영 호스트다. 확장 시 중앙 결정 저장소가 별도로 필요하다.
- 파일 손실 시 과거 연결을 완전히 복원할 수 없다. 이를 성공으로 숨기거나 모든 행을 자동 신규 처리하지 말고 검토·복구 절차로 전환한다.

## 6. 수정·삭제·재시도

### 수정

화면 로딩 시 원래 행 값과 itemId를 연결한다. excel_row만으로 DB 대상을 식별하지 않는다. 정렬·행 삽입 후에는 연결을 다시 계산한다.
PATCH에는 실제 변경한 필드만 보낸다. 원문 일시가 바뀌면 새 공지 등록을 안내하며 기존 공지를 자동 변경/삭제하지 않는다.
API 반영 후 파일 표시를 맞춘다. API/파일/연결 기록의 완료 상태를 구분해 작업 실패를 복구한다.

### 삭제와 수동 복원

엑셀 행 삭제는 itemId를 확인한 뒤 DELETE한다. 같은 공지를 참조하는 행이 여러 개면 한 번만 호출하고 현재 파일의 관련 표시를 함께 정리한다. 여러 선택 행이 있더라도 각 ID의 단건 처리 결과를 따로 표시한다.
DB 성공 후 파일 수정 실패는 파일 반영 대기로 남긴다. 파일만 삭제하고 DB 완료로 표시하지 않는다.
감지목록 삭제, 파일 자체 삭제, run JSON 삭제는 이번 DB 삭제와 연결하지 않는다.
수동 복원 전에는 이전 삭제의 미처리 작업을 정리한다. 복원 후 DB 재조회로 정상 상태를 확인하고 엑셀은 필요할 때 다시 구성한다. 기존 모든 파일의 자동 복원을 약속하지 않는다.

### 통신 실패

- timeout·네트워크 단절·일시 장애에 제한적 지수 백오프. 400/401/403/409/422는 무조건 재시도하지 않는다.
- import는 같은 payload로 재시도하며 UNIQUE와 linked 대상 재검증을 거친다.
- PATCH 응답 불명은 GET으로 확인하고 담당자 확인 없이 지연 재실행하지 않는다. 새로운 값을 덮어쓸 수 있다.
- DELETE 재시도는 수동 복원과 경합하지 않도록 한다. 삭제 후 복원한 공지를 예전 대기 요청이 다시 삭제하지 않게 한다.
- 파일/API 작업 시작 전에 처리할 원본·itemId·payload·단계를 durable 상태로 남긴다. 실패 후에만 기록하면 프로세스 종료 시 유실될 수 있다.
- API는 184 DB에 반영되면 성공이다. 더 이상 186 전송 대기나 서버 간 동기화 상태는 없다.

## 7. 최초 적재

최신 엑셀 파일 한 개를 명시적으로 선택한다. 오늘 파일을 제외하는 carryover 옵션을 초기 적재에 그대로 사용하지 않는다.
선택 파일의 현재 값을 기준으로 검증·후보 판정·저장한다. 과거 파일 디렉터리를 순회하지 않는다.
기존 DB와 충돌하면 저장 API의 현재 값 보존 규칙을 따른다. 최신 엑셀을 이유로 기존 DB를 일괄 덮어쓰지 않는다. 이후 날짜에 저장한 공지는 종료되어도 DB에 남는다.

## 8. 프론트 담당자에게 전달할 계약

프론트 실제 구현은 별도 담당이다. 이 프로젝트 담당자는 API 응답·로컬 검토 상태와 화면 요청의 서버 처리를 제공한다.

| 화면 데이터 | 전달 내용 |
|---|---|
| 수집 행 | 입력 6개 값·시작/종료·검토 상태 |
| 후보 | itemId·현재 6개 값·시작/종료·deletedAt |
| 비교 | 기관·일시·업무·사유 차이 강조 |
| 기존 공지로 연결 | 같은 구분·기관코드·일시의 정상 후보만 선택. 기존 값 사용, 수정 없음 |
| 새 공지로 등록 | 입력 값으로 등록. 정확한 동일 키는 중복 생성 불가 |
| 보류 | DB 저장 없이 로컬 검토 상태 유지 |
| 일시 변경 | 신규 등록 경로. 기존 공지 삭제는 별도 사용자 동작 |
| 삭제 후보 | 참고 표시만, 선택·자동 복원 불가 |

원문 ID가 없다는 이유만으로 선택창을 띄우지 않는다. 정확한 기존 키와 유효한 연결은 자동 처리한다. 날짜가 다른 공지를 같은 공지 후보로 보여주지 않는다.
프론트가 요청하는 LINK/NEW_ALLOW/HOLD는 SiteCheck 서버가 로컬 상태에 저장한다. 확정 LINK의 최종 검증은 외부 API가 한다. 세션·권한 검증을 생략하지 않는다.
일반점검은 checkType과 종료 범위, 정기점검은 checkType만 사용한다. NULL 시간을 임의 날짜로 바꾸지 않는다. itemId는 문자열이며 version을 요구하지 않는다.
타팀은 DB를 직접 SELECT한다. del_dt IS NULL, check_type 조건, DATETIME의 KST(+09:00) 해석과 NULL 규칙을 전달한다. 타팀의 업무 수정/삭제 권한은 없다.

## 9. 구현 순서와 검증

1. API 계약·DDL을 별도 API 프로젝트에 전달한다. 사용자가 DB 정보를 직접 제공한다.
2. 환경별 클라이언트와 원자적 로컬 상태 저장소를 만든다. 정규화 테스트 벡터를 API와 맞춘다.
3. 정확 조회→후보 조회→수동 결정→저장 흐름을 구현한다.
4. CLI·웹 수집·검토 추가에 공통 흐름을 연결한다.
5. 엑셀 수정·삭제 및 ID 매핑을 연결한다. 기존 기관코드+사유 append 중복 기준을 이 정책과 맞춘다.
6. 프론트 담당자에게 비교 DTO와 선택 동작을 전달한다.
7. 최신 엑셀 한 파일로 초기 적재를 검증한다.
8. API 담당자가 준 테스트 URL·인증·접속 조건으로 통합 테스트한다.
9. 검증 후 운영 API URL과 배포 절차를 확정한다. 실제 운영 데이터는 승인된 범위에서만 테스트한다.

필수 검증: 동일 공지 재수집, A사이트 점검/a사이트 점검의 업무·사유 대소문자 비교, 사유 수정 보존, 일시 변경 신규, LINK 재수집/재시작, 다른 일시 연결 거부, 삭제 후 자동 등록 금지, 수동 복원, 상태 파일 손상/쓰기 실패, API 성공/파일 실패, PATCH 결과 불명, 0이 아닌 소수 초 거부와 .000000 입력 허용, 일반·정기 조회, 최신 파일만 초기 적재.

문서 기준의 구현 선택은 로컬 수동 결정 저장과 일시 변경 신규 경로다. 기존 0.x 문서의 186 복제·outbox·last_seen_at·version·과거 파일 일괄 적재는 사용하지 않는다.
