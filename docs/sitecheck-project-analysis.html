SiteCheck 점검 공지
DB 저장 계획

엑셀의 점검 공지를 DB에 보관하고, 반복 수집은 중복 저장하지 않습니다. 담당자가 수정한 값은 유지하며, 일시가 바뀐 공지는 별도 등록합니다. 현재 공지와 종료된 공지 모두 하나의 테이블에서 관리합니다.

SECTION 01

최종 결정

최종 저장 구조
184 서버의 GDS.TB_SITE_CHECK 한 테이블타팀도 이 테이블을 읽기 전용으로 조회합니다. 186 복제 테이블·VIEW·서버 간 동기화는 만들지 않습니다. “184”는 서버 구분용 표현이며 실제 주소는 사용자가 API 구현 프로젝트에 직접 전달합니다.
항목결정
업무 범위전체 수집 시스템을 DB로 전환하지 않습니다. 엑셀 B:G의 업무 6개 값과 시작·종료 시각을 저장합니다.
보존 범위최초에는 최신 엑셀 한 파일만 적재합니다. 이후 등록된 공지는 종료되어도 보관하고, 수정 전 값의 변경 이력은 만들지 않습니다.
중복 기준구분·기관코드·기관명·일시 원문·업무의 식별 정규화 값(NFC·줄바꿈·앞뒤 공백·대소문자 통일). 사유와 시작·종료 파싱 값은 제외합니다.
재수집정확한 중복 또는 유효한 수동 연결이면 기존 DB 전체 값을 사용합니다. 자동 수집으로 담당자의 수정을 덮어쓰지 않습니다.
일시 변경대소문자 통일 후에도 일시 원문이 다르면 새 공지입니다. 이전 공지는 담당자가 필요 시 소프트 삭제합니다.
수정 충돌version 없이 마지막으로 DB에 반영된 명시적 수정이 우선합니다. 생략 필드는 기존 값을 유지합니다.
삭제·복원엑셀 행 삭제를 소프트 삭제 API와 연결합니다. 동일 공지 자동 재등록은 금지하고 복원은 수동 DB 작업으로만 합니다.
관측·수정 이력snapshot·last_seen_at·observedAt·수정자·수정 이력 테이블은 두지 않습니다. 자동 재수집만으로 up_dt도 바꾸지 않습니다.

last_seen_at을 빼도 되는 이유: 현재 요구는 “마지막으로 언제 수집됐는지”가 아니라 등록된 공지의 최신 내용과 종료 여부입니다. 원문 사이트에서 사라진 시점을 추적하거나 장기 미관측 공지를 자동 정리하는 기능은 제공하지 않습니다.

SECTION 02

현재 수집 구조

웹사이트 수집 → 점검 후보 추출 → 검토·반영 → 엑셀 생성의 기존 흐름은 유지합니다. DB 연동은 최종 엑셀 행이 결정되는 지점과 담당자의 행 단위 작업에 추가합니다.

현재 코드분석 결과와 연결 방향
excel_writer.py웹 수집 행은 일반점검으로 작성하며 정기점검은 YAML 설정에서 별도로 구성합니다. 제목에 정기점검 키워드가 있다는 것만으로 정기점검으로 자동 분류되는 구조는 아닙니다.
main.py / webserver.pyCLI와 웹 수집 모두 엑셀 생성 후 동일한 행 판정·API 연동 서비스를 사용하도록 연결합니다.
기존 엑셀 중복 처리carryover는 기관코드+일시 중심, 검토 페이지 추가는 기관코드+사유 중심입니다. 최종 DB 정책과 같지 않으므로 그대로 API 중복 기준으로 사용할 수 없습니다.
carryover.py최신 파일 선택과 이월 판정은 구분합니다. 최초 DB 적재에서 오늘 파일을 제외하면 안 됩니다. 종료가 없을 때 시작 시각을 대신 쓰는 기존 표시 판단을 DB 종료 값으로 저장하지 않습니다.

일반점검과 정기점검은 컬럼 구조가 같고 구분 조회만 필요하므로 테이블을 나누지 않습니다. check_type으로 구분합니다. 일시 원문은 필수지만 반복 일정은 실제 시작·종료 시각을 알 수 없어 NULL로 저장할 수 있습니다.

현재 코드에는 일시가 비는 경로도 있습니다. 앞으로 저장 경계에서 필수 검증을 적용하고, 누락된 행은 보완 대상으로 남겨야 합니다. 빈 일시를 임의 날짜나 빈 문자열로 DB에 저장하지 않습니다.

SECTION 03

중복과 수동 연결

1. 같은 내용은 하루가 지나도 한 건

어제와 오늘 동일한 5개 식별 값이 수집되면 같은 item_id를 사용합니다. 수집 회차나 엑셀 파일명을 식별키에 넣지 않습니다. 사유 A를 담당자가 B로 바꾼 뒤 A가 재수집되어도 B를 유지합니다.

입력 변화처리
사유만 다름기존 공지 사용. 기존 사유·업무 값·시작·종료를 모두 보존합니다.
파싱된 시작·종료만 다름기존 공지 사용. 시각 보정이 필요하면 명시적 PATCH로 수정합니다.
업무 A사이트 점검 / a사이트 점검같은 공지로 판정. 저장된 원문과 담당자 수정값을 유지합니다.
식별 정규화 후 일시 원문이 다름새 공지로 등록. 동일 URL·제목·사유라도 자동 연결하거나 이전 공지를 삭제하지 않습니다.
식별 정규화한 구분·기관코드·일시가 같고 기관명 또는 업무가 다름정확한 중복이 아니므로 후보를 보여주고 기존 연결·신규 등록·보류를 선택합니다.
삭제된 정확한 키 또는 유효한 연결재등록하지 않습니다. 복원은 담당자의 수동 DB 작업입니다.

2. 사람이 판단하는 선택지

수집 값과 기존 후보를 나란히 보여주고 구분·기관코드·기관명·일시·업무·사유·시작·종료·삭제 상태를 비교합니다. 기존 연결은 다른 일시를 선택할 수 없으며, 삭제 후보도 선택할 수 없습니다.

선택결과다음 수집
기존 공지 연결선택한 ID의 DB 값을 사용. 수집 값으로 덮어쓰지 않음입력 식별 값 → ID 연결을 로컬에 기억하고 API로 재검증
신규 등록별도 공지로 저장. 정확한 중복은 신규 강제 등록 불가신규 허용 결정을 기억하되 매번 정확한 중복 확인
보류DB 저장하지 않음. 보류 건수·사유를 명시다음 수집에도 보류 유지. 담당자가 결정 변경 가능

3. 해시만으로 수정 전 값을 기억할 수는 없음

dedup_hash는 현재 5개 식별 값을 대소문자 통일 후 계산한 SHA-256입니다. 사유 수정이나 대소문자만 다른 재수집에는 유지되지만, 식별 정규화 후 기관명·업무가 달라지면 바뀝니다. 따라서 변경 전 입력과 현재 공지의 연결은 SiteCheck의 output/state/{environment}/notice_state.json에 별도로 보관합니다. 수동 연결을 선택했을 때도 같은 기록을 사용합니다.

API 요청은 선택적 linkedItemId를 전달합니다. API는 대상의 구분·기관코드·식별 정규화한 일시가 입력과 일치하는지, 삭제되었는지, 입력의 정확한 키가 다른 ID에 이미 속하는지 매번 확인합니다. 연결이 유효하지 않으면 재검토하며 신규 등록으로 자동 전환하지 않습니다.

운영 전제: 한 운영 호스트에서 환경별 상태 파일을 공유하고 파일 잠금·원자적 저장·백업을 적용합니다. 기록이 유실되면 이전 수동 연결을 자동 복원할 수 없습니다. 여러 독립 호스트로 확장할 때는 연결 상태를 공유 저장소로 옮기는 설계를 다시 해야 합니다.

식별 정규화는 Unicode NFC, 줄바꿈 통일, 앞뒤 ASCII 공백 제거 뒤 Unicode casefold를 적용합니다. 내부 공백·요일·날짜 표기는 통합하지 않습니다. “같은 일시”는 실제 시각의 추정 일치가 아니라 식별 정규화한 일시 원문의 일치입니다. 원문 대소문자는 표시용으로 남깁니다.

SECTION 04

DB 설계

6개 업무 값 + 2개 시각 + 5개 관리 컬럼으로 총 13개입니다. 타팀도 동일 테이블에서 필요한 컬럼만 조회하며, 해시는 내부 중복 방어용으로 남깁니다.

컬럼타입설명
item_idBIGINT UNSIGNED공지 고유번호, PK
check_typeVARCHAR(20) NOT NULL일반점검 / 정기점검
institution_codeVARCHAR(10) NOT NULL정규화한 기관 코드
institution_nameVARCHAR(100) NOT NULL기관명 원문
schedule_textVARCHAR(200) NOT NULL일시 원문, 빈 문자열 금지(API 검증)
service_textVARCHAR(200) NOT NULL대상 업무, 빈 문자열 허용
reason_textVARCHAR(200) NOT NULL사유, 빈 문자열 허용
window_startDATETIME NULL초 단위 KST(+09:00) 시작 시각, 미확인·반복 일정은 NULL
window_endDATETIME NULL초 단위 KST(+09:00) 종료 시각, 미확인·반복 일정은 NULL
dedup_hashCHAR(64) UNIQUE사유 제외 5개 값의 SHA-256. 삭제 후에도 유지
crt_dtDATETIME NOT NULL최초 등록 시각 KST(+09:00)
up_dtDATETIME NOT NULL명시적 변경·삭제·수동 복원 시각 KST(+09:00)
del_dtDATETIME NULL삭제 시각 KST(+09:00). NULL이면 정상 공지

시간대와 정밀도: 다섯 DATETIME 컬럼은 모두 한국시각(KST, +09:00) 초 단위 DATETIME(DATETIME(0)과 동일)입니다. API는 시작·종료 및 조회 경계에 0이 아닌 소수 초가 오면 거부하며 반올림하지 않습니다. 생성·수정·삭제 시각도 소수점 없이 반환합니다. DATETIME 자체는 시간대 정보를 담지 않으므로 API의 모든 DB 연결도 +09:00으로 설정합니다.

문자열 비교: 일반 문자열 컬럼은 utf8mb4_unicode_ci를 사용합니다. 중복 판정은 API가 대소문자를 통일한 5개 값으로 계산한 해시와 dedup_hash의 UNIQUE가 담당합니다. 이 해시 컬럼의 ascii_bin은 유지합니다. SQL collation의 악센트 비교와 해시의 동일성 규칙은 완전히 같지 않으므로 SQL 문자열 비교만으로 중복을 확정하지 않습니다.

최종 DDL 전체 · 컬럼 COMMENT 포함
-- SiteCheck final design: one MySQL 8.0+ business table on the primary server.
-- Different schedule_text identities are separate notices; reason is not an identity field.
-- Explicit edits are last-applied-write-wins. Manual links live in SiteCheck state files.
-- The GDS schema must exist before execution. All DATETIME values are KST (+09:00) wall-clock values.
-- This session setting applies only to this connection; the API must set +09:00 on every DB connection.
-- The API validates nonempty values, time order and identity; UNIQUE protects duplicate writes.
SET NAMES utf8mb4 COLLATE utf8mb4_unicode_ci;
SET SESSION time_zone = '+09:00';

CREATE TABLE `GDS`.`TB_SITE_CHECK` (
                                 `item_id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '점검 공지 고유번호',
                                 `check_type` varchar(20) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '점검 구분\n 일반점검 또는 정기점검',
                                 `institution_code` varchar(10) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '대상 기관 코드',
                                 `institution_name` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '대상 기관명',
                                 `schedule_text` varchar(200) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '점검 일시 원문\n 실제 일정 또는 정기점검 일정',
                                 `service_text` varchar(200) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '점검 대상 업무',
                                 `reason_text` varchar(200) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '점검 사유',
                                 `window_start` datetime DEFAULT NULL COMMENT '점검 시작 일시\n 미확인 또는 정기점검 일정은 NULL',
                                 `window_end` datetime DEFAULT NULL COMMENT '점검 종료 일시\n 미확인 또는 정기점검 일정은 NULL',
                                 `dedup_hash` char(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL COMMENT '공지 중복 식별값\n 구분 및 기관코드 및 기관명 및 일시 및 업무의 구분값 삭제 후에도 유지',
                                 `crt_dt` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '최초 등록 일시',
                                 `up_dt` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '최초 변경 일시',
                                 `del_dt` datetime DEFAULT NULL COMMENT '삭제 일시\n NULL이면 정상 공지',
                                 PRIMARY KEY (`item_id`),
                                 UNIQUE KEY `uq_site_check_dedup_hash` (`dedup_hash`),
                                 KEY `ix_site_check_live_id` (`del_dt`,`item_id`),
                                 KEY `ix_site_check_type_end_id` (`check_type`,`del_dt`,`window_end`,`item_id`),
                                 KEY `ix_site_check_type_org_id` (`check_type`,`institution_code`,`item_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='기관별 점검 공지';

현재 DDL의 up_dt COMMENT는 “최초 변경 일시”이지만, 실제 API는 생성 후 명시적 수정·삭제·수동 복원 때마다 이 값을 갱신합니다. 테이블 적용 전 COMMENT를 실제 의미에 맞게 확정해야 합니다.

조회 성능과 무결성

(check_type, del_dt, window_end, item_id) 인덱스는 구분·미삭제 조건 다음에 종료 범위를 비교하는 조회를 고려했습니다. 종료 시각에 함수를 씌우지 않고 KST로 변환한 경계 값과 직접 비교합니다. 구분 없는 종료 범위 단독 조회까지 최적화한 인덱스는 아닙니다.

-- 일반점검: 종료 기준 범위 조회
SELECT item_id, check_type, institution_code, institution_name,
       schedule_text, service_text, reason_text,
       window_start, window_end, crt_dt, up_dt
FROM GDS.TB_SITE_CHECK
WHERE check_type = '일반점검'
  AND del_dt IS NULL
  AND window_end >= :from_kst
  AND window_end < :to_kst
ORDER BY window_end, item_id;

-- 정기점검: 종료 조건 없이 구분으로 조회
SELECT item_id, schedule_text, window_start, window_end
FROM GDS.TB_SITE_CHECK
WHERE check_type = '정기점검' AND del_dt IS NULL;

API 목록은 ID 내림차순을 사용하므로 종료 범위와 함께 쓰면 추가 정렬이 필요할 수 있습니다. 실제 데이터로 EXPLAIN을 확인해야 합니다. 후보 조회는 구분·기관코드 인덱스 후 API에서 식별 정규화한 구분·기관코드·일시를 다시 비교하며, 여러 페이지를 끝까지 확인합니다.

Application에서 후보 판정과 UX를 담당하고 API에서 중복·연결·필수값·기간 순서를 재검증합니다. DB의 UNIQUE는 동시에 같은 공지가 저장되는 것을 막습니다. NOT NULL만으로 빈 문자열·잘못된 구분·기간 역전이 막히지는 않으므로 업무 쓰기는 API로 제한합니다.

수정 시각은 API가 명시적으로 갱신합니다. 소프트 삭제한 키도 UNIQUE에 남으므로 중복 등록이 차단됩니다. version이 없어도 트랜잭션·행 잠금은 필요하지만 오래된 담당자 수정의 덮어쓰기 자체는 허용합니다.

프론트 및 타팀 전달

  • 프론트 구현은 별도 담당자 범위입니다. 비교 후보·보류 사유·행-ID·입력 식별 값과 LINK/NEW/HOLD 결정 정보를 전달해야 합니다.
  • 일반점검 종료 조건과 정기점검 구분 조건을 분리합니다. 종료된 공지를 화면에서 숨겨도 DB에서는 삭제하지 않습니다.
  • 타팀 DB 계정은 SELECT 전용입니다. del_dt IS NULL, KST(+09:00) 시각, 반복 일정의 NULL 처리, check_type 값을 전달합니다.
  • 복원은 del_dt 해제와 up_dt 갱신으로 수행합니다. 복원 전에 남아 있는 삭제 재시도 작업을 정리해야 다시 삭제되지 않습니다.

행별 CONFLICT 상태는 없습니다. 해시 충돌·잘못된 연결·입력 오류는 배치 전체 롤백입니다. DUPLICATE_IDENTITY는 PATCH의 식별키 충돌이며, 연결 오류는 IDENTITY_ALREADY_ASSIGNED 또는 LINK_TARGET_CHANGED로 구분합니다.

후보 조회는 SiteCheck의 사람 판단을 지원합니다. API의 신규 POST는 호출부에서 신규 등록을 결정한 명령으로 처리하되, 정확한 키 중복은 매번 재검사합니다. 후보의 존재만으로 API가 신규를 거부하지는 않습니다.

명시적 PATCH는 최신 잠금 행에 전달된 필드만 병합합니다. 동일한 최종 원문과 시각이면 NO_CHANGE, 다르면 UPDATED입니다. 정규화 키는 같아도 저장 원문이 달라지면 변경입니다. version은 요청하지 않습니다.

유연성과 남는 한계

단일 테이블과 nullable 시각은 현재 요구에 충분하고 구분별 조회도 단순합니다. 다만 수정 전 내용·마지막 수집 시각·담당자별 변경 경로는 복원할 수 없습니다. 후보 판정은 완전 자동이 아니며, 로컬 연결 상태가 보존되어야 담당자 결정이 재사용됩니다.

원문 표기 차이에 대한 유사도 병합, 여러 운영 호스트의 상태 공유, 별도 서버 복제, 수정 이력, 구분 없는 종료 단독 조회 최적화는 향후 요구가 생길 때 추가 설계합니다. 성능은 실제 데이터 양·분포·정렬 조합으로 확인해야 하며 현재 문서만으로 보장하지 않습니다.
